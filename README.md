# MakeAgent_001

IEC 62443-4-1 の開発プロセスに沿って、IEC 62443-4-2 のコンポーネント要件を満たす組込みソフト機能を実装するためのスキルとエージェント。インバータ、サーボアンプ、PLC などを対象とし、Claude Code と GitHub Copilot の両方で使う。

> 開発を支援する道具であり、適合や認証を保証するものではない。要件マップは独自要約で、規格原本との照合が必要 (issue #4)。規格本文は含まない。

## 使い方

Claude Code でも GitHub Copilot (VS Code のエージェントモード) でも、チャットで同じコマンドを使う。

| 操作 | コマンド |
|---|---|
| 初期設定 | `/iec62443 init` |
| issue を実装 (工程は issue に従う。なければ `code`) | `/iec62443 12` |
| 工程とモードを指定 | `/iec62443 standard spec 12` |
| 既存コードから文書を起こす | `/iec62443 reverse src/auth.c` |
| 文書、テスト、コードを整合させる | `/iec62443 reconcile` |
| 社内規定を登録 | `/iec62443 org-rules add 設計規定.md 部` |
| 改善提案 | `/iec62443 improve` |
| 1 つのエージェントだけに任せる | `/iec62443 code-reviewer src/auth.c を見て`、またはエージェントを直接選ぶ |

GitHub 上で Copilot に issue を割り当てて動かす場合は、「セキュリティ機能」テンプレートで起票する。issue に書かれたモードと工程で同じ手順が動く。

`/iec62443` を受けたエージェントがオーケストレーターとして動き、担当エージェントに仕事を割り振る。GitHub Copilot ではエージェント `orchestrator` を選んでも同じ。Claude Code では、サブエージェントは別のサブエージェントを呼べないので、`/iec62443` を通常の会話で使うか、`claude --agent orchestrator` で起動する。

### ツールごとの読込み先

| | Claude Code | Copilot (VS Code) | Copilot (GitHub 上) |
|---|---|---|---|
| 常時指示 | `CLAUDE.md` → `AGENTS.md` | `AGENTS.md` | `AGENTS.md` |
| 入口のスキル | `.claude/skills/iec62443/` (本体を指す) | `.github/skills/iec62443/` | 両方 |
| 役割別のスキル | `.github/skills/sec-*/` をパスで読む | `.github/skills/sec-*/` | `.github/skills/sec-*/` |
| エージェント | `.claude/agents/` (生成) | `.github/agents/` | `.github/agents/` |

定義の元は `.github/` の 1 か所だけ。`.claude/` 側は `python tools/sync_agents.py` で生成するので、直接は編集しない。

## エージェントの組織

役割ごとにエージェントを分け、それぞれが自分の役割に要るスキルだけを読む。組織図、スキルの割当て、作業のシーケンス図は [docs/organization.md](docs/organization.md) にある。

| 区分 | エージェント | 役割 |
|---|---|---|
| 統率 | orchestrator | 利用者 (設計者兼マネジメント) との窓口。計画し、担当に依頼し、報告をまとめる。成果物は書かない |
| 作成 | req-analyzer | 該当 CR の選定、脅威分析、要求の不備の洗い出し、要求仕様書 |
| | doc-writer | アーキテクチャ設計書、機能仕様書、ソフトウェア設計書、コードからの逆生成 |
| | test-designer | 単体、統合、システム試験のテスト仕様 |
| | coder | テストコードと実装 |
| | tester | テストの実施と結果の記録、実機試験の手順書 |
| レビュー | req-reviewer、doc-reviewer、test-design-reviewer、code-reviewer、test-reviewer | 上の 5 つをそれぞれ、作成者から独立して確認する。成果物は変更しない |
| 支援 | reconciler | 文書、テスト、コードのつじつま合わせ |
| | auditor | リリース前の棚卸し |
| | librarian | 社内規定の登録と索引の管理 |
| | improver | 学びからの改善提案 |

文脈を小さく保つ仕組み:

- オーケストレーターは文書やコードの中身を読まず、ID、ファイルの場所、各担当の報告 (10 行以内) だけを扱う。
- 各担当は、共通の `sec-base` と自分の役割のスキルだけを読む。ほかの役割のスキルは開かない。
- 成果物はファイルで受け渡し、依頼と報告には中身を貼らない。

エージェントに追加のスキルを読ませたいときは、`.sec62443/project.yml` の `agent_skills` に書く (プロジェクト単位)。全体の割当てを変える方法は [docs/organization.md](docs/organization.md) の「割当てを変える」を参照。

## 開発の流れ

文書を上流から順に作り、各工程で対になるテスト仕様を先に書く (TDD)。

| 工程 | 作る文書 (ID) | 先に作るテスト |
|---|---|---|
| `req` | 製品セキュリティ要求仕様書 (REQ) | システム試験仕様 (ST) |
| `arch` | 製品セキュリティアーキテクチャ設計書 (ARC) | 統合テスト仕様 (IT) |
| `spec` | 機能仕様書 (FS) | システム試験仕様 (ST)、統合テスト仕様 (IT) |
| `design` | ソフトウェア設計書 (SWD) | 単体テスト仕様 (UT)、統合テスト仕様 (IT) |
| `code` | ソースコード | 単体テストのコード (失敗を確認してから実装) |
| `it` / `st` | 統合テスト、システム試験の実施と結果 | — |

- 「機能仕様書」は外部から見える振る舞いを決める文書で、外部仕様書やソフトウェア要求仕様書にあたる。文書の名称と置き場所は `project.yml` の `docs` で社内の呼び方に変えられる。
- テスト設計は JSTQB の技法 (同値分割、境界値分析、デシジョンテーブル、状態遷移など) に沿う。セキュリティでは「拒否される側」の確認を必ず加える。
- 文書は ID 付きの項目の並びで書き、項目どうしの対応は `docs/security/trace.csv` の 1 か所で管理する。

### 順序どおりに進まないとき

どの工程からでも始められる。上流の文書がない、足りない、間違っている場合も止まらない。

| 状況 | 扱い |
|---|---|
| 要求仕様書に不備があるまま機能仕様書を書く | 仮定を置いて進め、未整合台帳に記録する。要求仕様書に足す項目が明らかなら、その場で「仮」として追加する |
| 下流で上流の誤りに気付いた | 確定済みの項目は書き換えず、台帳に案を書いて PR で判断を求める |
| 先にコードを書いた、既にコードがある | `reverse` でコードから設計と仕様を「逆生成」として起こし、今の振る舞いを固定するテストを書く |
| 後でつじつまを合わせる | `reconcile` が、上流や下流やテストのない項目、「仮」のままの項目、台帳の未解決行を洗い出し、承認された直し方を反映する |

- 未整合は `docs/security/gaps.md` (未整合台帳) に 1 件 1 行で残る。
- 項目を「確定」にするのは人。エージェントが付けるのは「仮」「逆生成」「要見直し」まで。
- リリース前の `audit` は、未解決の台帳の行と確定していない項目を不足として報告する。

## 社内規定の参照 (任意)

社、部、課の規定と文書の様式を、索引を通して必要な分だけ読ませる。

1. 適用先の `.sec62443/project.yml` に `org_rules_dir: .sec62443/org-rules` を設定する (`init` で尋ねられる)。
2. 規定をテキストか Markdown にして、`/iec62443 org-rules add <ファイル> [社|部|課]` で登録する。本文を 1 回読んで、索引 `index.md` に「適用する工程」と「要点 (3 行以内)」を書く。要点は登録時に確認する。
3. 以後の作業では索引だけを読み、今の工程に当てはまる規定の要点に従う。standard では必要な規定の本文も開く。

- 規定は社、部、課を足し合わせて適用する。矛盾するときは厳しいほうに従い、未整合台帳に記録して人に確認する。
- プロジェクト固有ルール (`rules.md`) やスキルの手順は、社内規定を緩める方向には働かない。
- 承認、押印、レビュー会議など、エージェントが用意できないものは PR に人への依頼として挙がる。
- 規定を git で管理するかどうかは `init` で選ぶ。このリポジトリのような公開の場所には置かない。Word、Excel、PDF のままでは読めないことがあるので、テキストに変換して渡す。

## モード

| モード | 用途 | 消費 |
|---|---|---|
| lite (既定) | 日常の作業。作成の担当だけを呼び、レビュー担当は呼ばない。規定は索引の要点だけを見る | 小 |
| standard | 新規のセキュリティ機能や外部インタフェースの変更。脅威分析、該当するテスト技法すべて、規定の本文、各 reviewer による独立レビューを追加 | 中 |
| audit | リリース前の棚卸し。未整合、CR の充足状況、4-1 の証跡の不足を一覧にする | 大 |

## 目標セキュリティレベル (SL) の切替

どの SL まで満たすかは、適用先プロジェクトの `.sec62443/project.yml` の `target_sl` で決まる。スキルは要件マップから、必要な SL がこの値以下の CR と強化要件 (RE) だけを選ぶ。

```yaml
target_sl: 1   # 1〜4。SL1 でよければ 1、SL2 が必要なら 2 (既定)
```

| やりたいこと | 方法 |
|---|---|
| 製品全体を SL1 でよいことにする | `target_sl: 1` にする |
| 製品全体を SL2 以上にする | `target_sl: 2` (または 3、4) にする |
| 一部の CR だけ扱いを変える | `.sec62443/rules.md` に CR、扱い、理由を 1 行で書く (下の例) |
| 1 つの issue だけ変える | issue の本文に「この issue は SL1 で実装」のように理由付きで書く |

`rules.md` の例:

```
- CR 1.1 は SL2 の RE(1) まで実装する (全体は SL1 だが、保守ツール接続は個人を特定したいため)
- CR 2.2 は対象外 (無線インタフェースを持たないため)
- EDR 3.14 RE(1) は次期ハードで対応。現行機は SL1 相当 (セキュアブート非対応の MCU のため)
```

注意:

- `target_sl` を変えても、実装済みの機能は自動では見直されない。上げた後は `/iec62443 audit` で不足を洗い出す。
- SL を下げる、CR を対象外にする、という判断は製品のリスク評価に基づいて人が行い、理由を残す。エージェントは `rules.md` と issue に書かれた判断に従うだけで、自分では下げない。

## 規格本文の参照 (任意)

このリポジトリには規格本文を含めていない。既定では要件マップ (独自要約) だけで動く。購入済みの規格を適用先のローカルに置くと、スキルは該当する要件の本文を読んで文書の項目とテストを作る。

1. 規格を AI サービスに読ませてよいか、ライセンス条件と社内規程を確認する。
2. 適用先の `.sec62443/project.yml` に `standard_docs: .sec62443/standards` を設定する (`/iec62443 init` で尋ねられる)。
3. そのディレクトリを `.gitignore` に入れる (`init` が追加する)。
4. 要件 1 つを 1 ファイルにして置く。全文を 1 ファイルで置くと毎回の消費が大きくなる。

```
.sec62443/standards/
  4-2/CR-1.1.md
  4-2/EDR-3.14.md
  4-1/SR.md
```

- 置いたファイルは git に入らないので、開発者ごとに用意する。GitHub 上で動く Copilot からは見えず、その場合は要件マップだけで動く。
- ファイルがある要件は本文を正とし、ない要件は要件マップで進めて issue に「本文未参照」と記録する。
- 本文と要件マップが食い違うと `lessons.md` に記録され、`/iec62443 improve` で要件マップの修正提案になる。
- 本文は issue、PR、文書に書き写されない (ID と要約のみ)。

適用先のプロジェクトで `init` を実行すると作られるもの:

```
.sec62443/project.yml             目標 SL、製品種別、言語、ツール

.sec62443/standards/              規格本文の抜粋 (任意、git 管理外)
.sec62443/org-rules/              社内規定の索引と本文 (任意)

docs/security/gaps.md             未整合台帳
docs/security/*.md, test/*.md     各工程を最初に実行したときに作られる文書とテスト仕様
```

## 改善ループ

1. 作業中に手順どおりに進まなかった点を `lessons.md` に 1 行残す
2. `improve` が学びを「固有 / 一般 / 一過性」に分ける
3. 固有はそのプロジェクトの `rules.md` へ、一般はこのリポジトリへの issue (ラベル `improvement-loop`) へ
