# improve: 改善ループ

スキルをプロジェクトに合わせて育てる。一般手順 (スキル本体) とプロジェクト固有の事情 (`.sec62443/rules.md`) を分けることで、スキルを更新しても固有の調整が消えないようにする。

## 入力

- `.sec62443/lessons.md` の未処理の行 (行頭が `- ` のもの)
- 余裕があれば、直近にマージされた PR のレビュー指摘 (`gh pr list --state merged -L 5` から必要なものだけ)

## 手順

1. 学びを 3 つに分ける。
   - **固有**: このプロジェクトだけに当てはまる (特定の MCU、ライブラリ、社内規約、試験設備) → `rules.md` に 1〜2 行のルールとして追記する案
   - **一般**: 他の製品でも当てはまる → スキル本体の修正案。スキルの配布元リポジトリへの issue 下書き (ラベル `improvement-loop`) にする
   - **一過性**: 再発しそうにない → 何もしない
2. 同じ趣旨のルールが既にあれば追記せず、既存の行を直す。`rules.md` が 40 行を超えたら、使われていないルールの削除も提案する。常に読まれるファイルなので短く保つ。
3. 案を一覧で示し、承認されたものだけ反映する。issue の起票も承認を得てから行う。
4. 処理した lessons の行は `- ` を `- [済] ` に変える。

## よい固有ルールの形

状況と行動が 1 行で分かり、理由が添えてある。

```
- パラメータ書込みの検証は param_table.c の範囲定義を使う (独自の範囲チェックを書くと二重管理になるため)
```
